## Architecture

- `src/app/(auth|formateur|maintenance|partenaire|admin)/` : un groupe de routes par espace utilisateur.
- `src/app/api/` : routes API et webhooks (Clerk).
- `src/lib/supabase/` : clients Supabase (`server.ts`, `client.ts`). Toujours passer par ces helpers.
- `src/lib/validations/` : schémas Zod, partagés entre formulaires et Server Actions.
- `src/lib/exports/` : génération du Word des bilans (docx). Le PDF final est déposé par la Direction, pas généré.
- `src/lib/offline/` : Dexie et synchronisation des brouillons.
- `src/components/ui/` : composants shadcn/ui (générés, modifier avec parcimonie).
- `supabase/migrations/` : schéma SQL et politiques RLS. `supabase/functions/` : Edge Functions.
- `src/proxy.ts` : protection des routes par rôle via Clerk (Next.js 16 appelle « proxy » l'ancien middleware). Les pages réservées à certains rôles sont listées dans `RESTRICTED_PATHS` (`src/lib/auth/roles.ts`).

Préférer les Server Components et les Server Actions. Utiliser `"use client"` uniquement pour l'interactivité (formulaires, caméra, géolocalisation, mode hors ligne).

## Rôles et sécurité — règles impératives

Rôles : `formateur`, `maintenancier`, `directeur_partenaire`, `admin_pedagogie`, `admin_rh`, `admin_maintenance`, `super_admin`. Stockés dans `publicMetadata.role` de Clerk et lus par Supabase via le JWT Clerk.

1. **Double contrôle** : toute donnée protégée est filtrée par le proxy/les Server Actions **et** par une politique RLS. Ne jamais compter sur l'interface seule.
2. **RLS activée sur toutes les tables**. Chaque nouvelle table arrive avec ses politiques dans la même migration.
3. **`SUPABASE_SERVICE_ROLE_KEY` uniquement côté serveur** (Server Actions, routes API, Edge Functions). Jamais dans un fichier `"use client"` ni dans une variable `NEXT_PUBLIC_`.
4. **Documents du personnel** (CV, CNI, photos) : bucket privé, accès par URL signées de courte durée, réservé à `admin_rh` et `super_admin`.
5. **Aucune suppression physique** de données métier : utiliser des statuts (`archive`, `inactif`…). Les actions sensibles écrivent dans `audit_log`.
6. **Ne jamais committer** `.env.local` ni de clé réelle.

## Règles métier clés

- **Pointage en deux temps** : à l'**arrivée**, le formateur pointe **sans code** (heure + géolocalisation, rayon défini par école dans `schools`) ; échec horaire → statut `retard` ; hors rayon ou géolocalisation refusée → `a_verifier`. À la **descente**, il saisit le **code du jour** donné par le directeur **après le cours** : la base n'accepte le code qu'à partir de la **fin exacte du créneau**, et sa saisie enregistre l'heure de descente. Un seul pointage par formateur, école et créneau. Limiter les tentatives de code (5 faux → 15 min, un code donné trop tôt n'use pas les essais). Les anciens pointages (`requires_departure` faux) gardent l'ancien fonctionnement.
- **Rapport journalier** : lié à un pointage ; il contient **plusieurs cours** (heures de début et de fin, classe, thème, effectif des élèves présents ; `daily_reports.courses`, jsonb, 1 à 12) et **une seule section « Difficultés rencontrées »** à la fin (pannes de machines, qui créent des tickets). Son formulaire **ne s'ouvre que lorsque la descente est validée** : le formateur saisit le code du directeur (accepté à la fin exacte du créneau) ou, si le directeur est absent, la Direction valide la descente avec un motif. La base (`guard_report_window`) refuse la **création** d'un rapport tant que `attendances.departed_at` est vide (les anciens pointages et les brouillons déjà créés ne sont pas concernés). Une fois ouvert, l'envoi à la Direction n'est jamais bloqué. Statuts `brouillon` → `soumis` → `valide` | `valide_avec_corrections` | `a_modifier` (commentaire obligatoire). Un rapport validé est verrouillé. Chaque correction de la Direction va dans `report_revisions`.
- **Pannes** : chaque panne saisie dans un rapport crée un ticket dans `maintenance_tickets` ; un doublon sur une machine déjà en panne se rattache au ticket ouvert.
- **Bilans** : seuls les rapports validés sont inclus. Export .docx éditable, puis PDF final figé envoyé au portail partenaire.
- **Règlement intérieur** : versionné ; une nouvelle version doit être ré-acceptée (`document_acceptances`).

## Conventions de code

- TypeScript strict, pas de `any`. Utiliser les types générés de `src/types/database.ts`.
- Valider toute entrée utilisateur avec Zod, côté client **et** serveur.
- **Formulaires** : utiliser `src/components/ui/form.tsx` (`Field`, `FormError`, `FormStatus`, `FormActions`) et `ui/select.tsx` ; ne pas réécrire un libellé, un message d'erreur ou une rangée de boutons à la main. Le résultat d'une action se place **au-dessus** des boutons (visible sur téléphone). Le nom d'une personne se saisit dans **un seul champ « Nom complet »** (au moins deux mots, le dernier est le nom de famille : `splitFullName`).
- Composants en PascalCase, fichiers de composants en kebab-case, hooks préfixés `use`.
- Style avec Tailwind uniquement ; couleurs de la charte (Bleu / Blanc / Gris) via les variables de thème, pas de valeurs codées en dur.
- Mobile d'abord : tester à 360 px de large. Penser connexion lente (images compressées, pas de chargements inutiles).
- Dates : `date-fns` avec la locale `fr`, fuseau `Africa/Dakar`, affichage `jj/mm/aaaa`.
- Commits : Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`).
- Branches : `feature/<nom>` depuis `develop`.
